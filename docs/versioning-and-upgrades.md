# 版本与升级流程

## 1. 三种独立版本

| 版本 | 例子 | 变化对象 |
| --- | --- | --- |
| 契约版本 | `sensor-event@1.0.0` | 字段、类型与语义 |
| 传感器实现版本 | `tracker.yolo@0.2.0` | 算法、配置默认值、后端 |
| 模型/资产版本 | SHA-256 + 上游版本 | 权重、模板、语言数据 |

三者不得用一个“项目版本”含糊代替。

## 2. SemVer 规则

- **MAJOR**：删除/重命名字段、改变单位/坐标/时间语义、状态含义不兼容；
- **MINOR**：新增可选字段、能力或向后兼容配置；
- **PATCH**：文档澄清、错误修复且输出语义不变。

在 `0.x` 阶段仍按同样纪律记录破坏性变化，但允许快速迭代。稳定接口进入 `1.0.0` 前必须有至少两个独立传感器适配和一个下游应用验证。

## 3. 成熟度

```text
planned → incubating → candidate → stable → deprecated → retired
```

- `planned`：只有契约/清单；
- `incubating`：有适配器和 L0/L1 测试；
- `candidate`：完成来源对照和受控基准；
- `stable`：下游试点通过，兼容和回退已验证；
- `deprecated`：仍可用但有替代方案和截止版本；
- `retired`：不再发布或支持。

## 4. 升级步骤

1. 创建 [`SENSOR_UPGRADE.md`](../templates/SENSOR_UPGRADE.md) 记录；
2. 锁定来源仓库完整 commit/tag、文件和许可证；
3. 分类变化：纯适配、修复、算法变化、配置变化、模型变化；
4. 固定升级前回放集和结果；
5. 实施时保留原算法路径，不在同一变更混入无关重构；
6. 运行 L0/L1，对比输出、性能和失败样本；
7. 高风险升级补充 L2/L3；
8. 更新清单、Schema/示例、CHANGELOG 和迁移说明；
9. 在一个下游项目灰度，保留 feature flag 或版本回退；
10. 达到预先门槛后再提升成熟度。

## 5. 兼容策略

- 读取方至少支持当前 MAJOR 的最近两个 MINOR；
- 未识别的可选 payload 字段应忽略并保留；
- 不认识的状态或单位必须拒绝或明确降级，不能猜测；
- 废弃字段至少保留一个 MINOR 周期，并提供转换示例；
- 事件升级工具不得覆盖原始文件，默认输出到新路径。

## 6. 来源同步策略

本仓库不是现有仓库的镜像。来源项目继续独立开发时：

- 定期盘点候选 commit；
- 只挑选明确、可验证的变化；
- 每次升级记录“来源行为”和“适配层行为”的差别；
- 不以日期或 README 相似度代替 commit SHA；
- 上游变更未通过本仓库门禁时，现有稳定适配版本保持不动。

## 7. 回退

每次 candidate/stable 升级必须写明：上一可用版本、配置/数据是否可逆、模型资产如何恢复、下游 feature flag 和回退验证结果。不能回退的数据迁移属于破坏性变化。
